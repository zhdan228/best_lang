A.1.1  Числовые типы разного размера (уровень 1)
Язык поддерживает восемь целочисленных типов: int8, int16, int32, int64 — знаковые, и uint8, uint16, uint32, uint64 — беззнаковые.
Вещественных типов два: float32 и float64. Итого десять числовых типов против одного в базовом варианте.
Все ключевые слова зарегистрированы в таблице лексера и распознаются как отдельные токены
(src/lexer.cpp, строки 20-26). Числовой литерал без суффикса получает тип int32 по умолчанию.
Если нужен другой тип — суффикс пишется сразу после числа без пробела: 42i8, 255u8, 1000u32, 3.14f32.
Лексер читает цифры, затем проверяет наличие суффикса, перебирая таблицу от длинных к коротким
(i64 перед i6, чтобы не ошибиться в подстроке) и сравнивая с текущей позицией (строки 118-136).
После разбора суффикса значение сразу усекается до нужного размера через C++-приведение.
Например, 300i8 усекается до 44 — это wrap-around, как в большинстве языков с фиксированной разрядностью.
Лексер кладёт готовое число в объединение (union) нужного поля токена: num.i8, num.i32 и так далее.
В семантике каждый тип хранится как объект Type с Kind-меткой. Арифметика в VM разделена:
знаковые операции (IADD, ISUB...) работают с int64, беззнаковые (UADD, USUB...) с uint64 —
это позволяет не смешивать семантику знакового и беззнакового деления.

A.1.3  Динамические массивы (уровень 1)
В языке есть два вида массивов. Фиксированный [T; N] — размер известен на этапе компиляции,
создаётся сразу с нужным количеством ячеек. Динамический [T] — без указания размера,
может расти и уменьшаться во время выполнения. Поддерживаемые операции: push, pop, len, get.
Литерал динамического массива обрабатывается при lowering отдельно от фиксированного.
Для фиксированного [1, 2, 3] lowering создаёт инструкцию NewArray с нужным размером,
затем по одной инструкции ArraySet для каждого элемента с его индексом и значением (src/lowering.cpp, строки 373-377).
Для динамического сначала создаётся пустой массив через NewDynArray,
затем каждый элемент добавляется по очереди через ArrayPush (строки 368-372).
Кодоген транслирует это в опкоды: NEW_ARRAY (0x70) или NewDynArray, затем ARRAY_SET (0x72) или ARRAY_PUSH (0x74).
В VM фиксированный массив создаётся через NEW_ARRAY: читает из байткода размер,
выделяет ArrayObj с заранее заполненными нулевыми ячейками и кладёт его на стек (src/vm.cpp, строки 258-261).
Динамический начинается с пустого ArrayObj и наполняется через ARRAY_PUSH (строки 285-288).
ArrayObj внутри VM — это просто std::vector<Value>. ARRAY_GET снимает со стека индекс и массив,
проверяет что индекс в допустимых пределах, возвращает элемент (строки 263-270).
Если индекс выходит за границы — runtime error с сообщением о конкретном индексе и размере.
ARRAY_POP снимает последний элемент и кладёт его на стек, уменьшая вектор. ARRAY_LEN возвращает текущий размер.
Оба вида массива хранятся в Value через shared_ptr на ArrayObj, потому что массив может быть
произвольного размера и неизвестного на этапе компиляции. Когда массив передаётся в функцию,
вызывается deep_copy (src/vm.cpp, строки 31-47): создаётся новый ArrayObj и рекурсивно копируется
каждый элемент. Это value semantics — изменения внутри функции не трогают оригинал снаружи.

A.1.4  Кортежи (уровень 1)
Кортеж — анонимная структура из нескольких значений разных типов. Синтаксис: (a, b, c).
Обращение к элементам через .0, .1, .2 и так далее.
Реализовано через уже существующий механизм структур. Кортеж (38, 57) превращается в структуру
с именем __tuple__ и полями f0, f1. Доступ через .0 парсер переводит в .f0 при построении AST —
это происходит на этапе анализа выражений поля структуры в семантике.
Зачем так, а не отдельное представление: не нужно делать отдельный узел в IR и отдельные опкоды в VM —
всё работает через NewStruct, FieldGet, FieldSet, которые уже есть. Единственное что добавлено —
обработка синтаксиса (a, b) в парсере и распознавание числовых полей .0, .1 в семантике,
которая превращает их в f0, f1. Тип кортежа — TupleType. Кортежи (int32, float64)
и (float64, int32) — разные типы, потому что порядок элементов является частью типа.

A.1.6  Nullable-типы (уровень 1)
Тип T? означает что переменная может хранить либо нормальное значение типа T, либо null — отсутствие значения.
Работает для любого типа: int32?, float64?, string?, пользовательских структур, полей в структурах.
В системе типов компилятора T? — это отдельный вид NullableType, обёрнутый вокруг T.
Семантика знает что int32? и int32 — разные типы, но разрешает присваивать int32 в int32? без явного приведения
(src/semantic.cpp, строки 1266-1267): это null_compat — если тип переменной nullable
и тип правой части либо тоже nullable, либо равен внутреннему типу (тому самому T) — присваивание разрешено.
В VM никакой обёртки или контейнера нет. Value — это уже размеченное объединение с тегом Kind.
Int32? переменная физически хранит обычный Value: когда в ней лежит число — Kind::Int с числом в поле i.
Когда в ней null — Kind::Unit с пустым значением. Это тот же самый слот памяти, просто тег меняется.
Разберём конкретно что происходит при var n: int32? = null:
лексер видит null и выдаёт токен Null, парсер строит NullLitExpr,
семантика присваивает ему тип nullable(void) — специальный пустой nullable (строка 1128).
При проверке совместимости: объявленный тип int32? является nullable, тип инициализатора тоже nullable — разрешено.
При lowering NullLitExpr превращается в операнд ConstUnit (src/lowering.cpp, строка 407).
Кодоген видит ConstUnit и генерирует опкод PUSH_UNIT (0x04) — он кладёт на стек Value{Kind::Unit}.
Это значение сохраняется в слот переменной n через STORE.
Когда потом пишешь n = 317 — число 317 кладётся как Value{Kind::Int, i=317} в тот же слот.
Слот просто перезаписывается: теперь там Int, а не Unit.
Проверка n == null: lowering создаёт IEQ между операндом переменной n и ConstUnit.
В VM инструкция IEQ снимает два значения со стека. Если хотя бы одно из них Kind::Unit,
сравниваются только теги Kind (src/vm.cpp, строки 497-500). Если n хранит Int, теги разные — false.
Если n хранит Unit, оба Unit — true. Никаких специальных nullable-опкодов нет:
обычный IEQ, но с дополнительной веткой для Unit. Это же работает для любого T? без изменений в VM.

A.1.8  Неявное приведение типов (уровень 1)
Язык автоматически расширяет числовые типы там, где это однозначно безопасно.
Цепочка: int8 -> int16 -> int32 -> int64 -> float64. Беззнаковые: uint8 -> uint16 -> uint32 -> uint64.
Расширение происходит в семантическом анализаторе через функцию maybe_widen (src/semantic.cpp, строки 667-679).
Она получает выражение и желаемый тип. Если текущий тип находится ниже по цепочке,
функция оборачивает выражение в CastExpr с нужным целевым типом.
Этот узел затем превращается в IR-инструкцию Cast, а VM выполняет преобразование.
Пример: при val x: int64 = some_int32_value семантика видит, что левая часть int64,
а правая int32. Вызывается can_widen(int32, int64) — возвращает true.
Вокруг правой части ставится неявный Cast до int64. Сужение только явное (через as),
потому что оно может потерять данные. Расширение — никогда.

A.2.8  Перегрузка функций (уровень 2)
Можно объявить несколько функций с одним именем, если у них различаются типы параметров.
Компилятор сам выбирает нужную при вызове.
При регистрации функции в семантике, если имя уже занято, оба варианта кладутся в список
перегрузок (overloads) в таблице символов (src/semantic.cpp, строки 1462-1474).
При каждом вызове, если список перегрузок для данного имени существует, запускается разрешение.
Разрешение двухпроходное. Сначала ищется точное совпадение: типы всех аргументов должны
совпасть с типами параметров точно. Если нашли — используем. Если нет — второй проход
ищет совпадение с допустимым неявным расширением (это задание A.3.1).
Чтобы избежать путаницы имён, каждая перегрузка получает уникальное мангированное имя вида
describe@int32 или process@int64. Функция mangle (src/semantic.cpp, строка 510) берёт базовое имя
и добавляет через символ @ типы параметров. Вызывающий узел AST переименовывается
в это мангированное имя ещё в семантике, поэтому в IR и байткоде все вызовы уже однозначны.

A.2.12  Методы структур (уровень 2)
Конструкция impl TypeName позволяет определить функции, привязанные к структуре. Вызов: obj.method().
При парсинге impl-блока методы читаются как обычные функции, но их имена автоматически
квалифицируются: метод describe внутри impl Point становится Point::describe.
Именно под таким именем он попадает в глобальную таблицу символов и в байткод.
Первый параметр метода — всегда self с типом самой структуры.
Когда вызывается obj.describe(), семантика распознаёт это как вызов метода,
подставляет obj как первый аргумент и генерирует вызов Point::describe.
В байткоде вызов метода использует CALL_METHOD (опкод 0x56), а не обычный CALL (0x53).
Разница принципиальная: CALL_METHOD не делает deep_copy первого аргумента (self),
тогда как CALL копирует все аргументы (src/vm.cpp, строки 548-558).
Это нужно чтобы мутации полей структуры внутри метода были видны снаружи.
Если бы self тоже копировался, изменения терялись бы.

A.2.16  Обобщённые типы (уровень 2)
Функции и структуры могут принимать параметры типов, которые конкретизируются при использовании.
Синтаксис: fun identity<T>(x: T): T или struct Pair<A, B>.
Реализовано через мономорфизацию: для каждой комбинации конкретных типов создаётся отдельная
копия функции или структуры. Шаблон хранится в таблице generic_funs (src/semantic.cpp).
При вызове identity<int32>(x) семантика берёт шаблон, подставляет T = int32 и создаёт новую
функцию identity@int32 с полностью конкретными типами. Эта функция добавляется в IRProgram как обычная.
Подстановка типов выполняется через subst_type (src/semantic.cpp, строки 25-66),
которая рекурсивно обходит дерево типов и заменяет TypeParam на конкретный тип.
Для Pair<int32, string> все вхождения A заменяются на int32, B на string.
Мономорфизация выбрана потому что для каждого набора типов генерируется специализированный байткод
без лишних проверок — это проще реализовать и быстрее исполняется.

A.3.1  Перегрузка с неявными приведениями (уровень 3, расширяет A.2.8)
Расширение обычной перегрузки (A.2.8): если точного совпадения типов нет,
разрешитель пробует найти перегрузку куда аргументы можно привести расширяющим преобразованием.
Второй проход разрешения (src/semantic.cpp, строки 965-987): для каждого кандидата проверяется
можно ли расширить каждый аргумент до типа соответствующего параметра через can_widen.
Если такой кандидат найден ровно один — он выбирается. Если несколько — ошибка неоднозначности.
Пример: есть overload process(int64). При вызове process(42i32) — точного совпадения нет (int32 != int64).
Второй проход проверяет can_widen(int32, int64) — возвращает true, один кандидат найден.
Тогда вокруг аргумента ставится неявный Cast до int64, имя переименовывается в process@int64.
Приоритет точного совпадения над приведением принципиален: если есть и process(int32) и process(int64),
вызов с int32-аргументом выбирает первую без каких-либо приведений.

A.3.7  Автовывод типовых аргументов (уровень 3, расширяет A.2.16)
Обобщённую функцию можно вызвать без явного указания типового аргумента:
вместо identity<int32>(x) можно писать identity(x) — компилятор сам выведет T = int32 из типа аргумента.
Вывод реализован через унификацию. Функция infer_types (src/semantic.cpp, строки 109-138)
принимает шаблонный тип параметра (может содержать TypeParam) и реальный тип аргумента,
и заполняет словарь bindings вида T -> int32.
Если шаблонный тип — это TypeParam с именем T, сразу записывает T = реальный тип.
Если шаблонный тип составной (например [T] для массива), рекурсивно разбирает его
и выводит T из типа элемента аргумента.
После заполнения bindings компилятор проверяет что все параметры выведены (строки 876-880).
Если хоть один не выведен — ошибка. Если все выведены — через subst_type подставляет конкретные
типы, создаёт мономорфную копию и переименовывает вызов. Вывод поддерживает вложенные типы:
для Pair<int32, int32> выводит оба параметра A и B независимо.

B.2.1  Промежуточное представление (IR) (уровень 2, сосед B.2.5)
Между семантическим анализом и кодогенерацией есть явная фаза промежуточного представления —
трёхадресный код (three-address code). Каждая инструкция имеет вид: dst = op(src1, src2).
Зачем отдельная фаза: семантика работает с деревом выражений, где вложенность произвольная.
Кодоген работает с линейной последовательностью инструкций. IR — мост между ними.
Без IR кодоген пришлось бы делать рекурсивным обходом дерева, что усложняет оптимизации и отладку.
Lowering (src/lowering.cpp) обходит AST и для каждого выражения возвращает операнд —
куда положен результат: временная переменная t0, t1, или уже константа.
Для выражения 2 + 3 * 4 lowering создаёт две инструкции: t0 = 3 * 4, t1 = 2 + t0.
Управляющие конструкции (if, while) разворачиваются в метки и условные прыжки.
IR можно посмотреть флагом --dump-ir. Если оба операнда константы, оптимизатор свернёт
арифметику и в выводе будет просто Copy t1 = 14.
Структуры данных IR в src/ir.hpp: Operand — вариант из TempVar, LocalVar, ConstInt, ConstString,
ConstUnit и других. Каждая инструкция — тоже вариант: IBinInstr, Copy, JumpFalse, ReturnVal, Print, Call.

B.2.5  Байткодная виртуальная машина (уровень 2, сосед B.2.1)
Вместо прямой интерпретации AST компилятор транслирует IR в бинарный байткод,
который исполняет отдельная стековая VM (blvm).
Архитектура: VM хранит стек значений (stack) и стек фреймов (frames).
У каждого фрейма есть слоты — ячейки для параметров и локальных переменных.
Все вычисления идут через стек: операнды кладутся на него, инструкция снимает нужное количество,
вычисляет результат и кладёт обратно.
Значение Value — размеченное объединение с тегом Kind: Int, UInt, Float, Bool, Char, Str, Array, Struct, Unit.
Тег нужен чтобы VM знала как интерпретировать биты и какую операцию применить.
Вызов функции: CALL снимает аргументы со стека справа налево, создаёт новый фрейм,
deep_copy-ит каждый аргумент в слот (чтобы функция не могла случайно изменить переменные вызывающего),
передаёт управление в код вызываемой функции. RET_VAL кладёт возвращаемое значение
на стек предыдущего фрейма и уничтожает текущий.
CALL_METHOD делает то же, но первый аргумент (self) без копирования — чтобы методы
могли изменять поля структуры.
Всего около 60 опкодов, сгруппированных по диапазонам: 0x01-0x14 константы и переменные,
0x20-0x2F арифметика, 0x30-0x32 логика, 0x40-0x4F сравнения, 0x50-0x56 управление потоком,
0x70-0x75 массивы, 0x80-0x83 структуры, 0xB0-0xB1 вывод (src/codegen.hpp).

B.1.12  Сериализация байткода (уровень 1, требует B.2.5)
Компилятор записывает байткод в файл .blc, blvm читает его и исполняет независимо.
Скомпилировать и запустить можно раздельно: myc prog.bl -o prog.blc, потом blvm prog.blc.
Формат бинарный с фиксированной структурой. Первые 24 байта — заголовок.
Дальше четыре секции: пул констант, секция функций, глобальные переменные, таблица отладочных строк.
Заголовок хранит: магическое число BL (байты 0x42 0x4C), версию формата (байт 0x01),
затем пять 4-байтовых чисел в little-endian: смещение пула, смещение функций,
смещение отладочной секции, индекс функции main, смещение глобальных переменных.
Смещения нужны чтобы VM могла сразу перейти к нужной секции без линейного чтения.
Пул констант — дедуплицированная таблица всех литеральных значений программы:
строк, целых, вещественных, имён функций. Каждая запись начинается с тега типа
(INT64 = 0x01, STRING = 0x05, FNAME = 0x06), потом идут данные.
Строки хранятся как 4 байта длины плюс байты UTF-8. Дедупликация: если такое значение уже есть
в пуле, возвращается прежний индекс без добавления новой записи (src/codegen.cpp, строки 58-65).
При загрузке VM проверяет магическое число и версию: если не совпадают — отказывается запускать
(src/vm.cpp, строки 120-123). Это защита от запуска файла несовместимой версии.

    StringLit("Hello, World!")
    RParen
    Semicolon
    Return
    IntLit(0)   суффикса нет, тип int32 по умолчанию
    Semicolon
    RBrace

Строковый литерал читается отдельно: лексер видит открывающую кавычку, накапливает символы в строку,
обрабатывает escape-последовательности если есть, закрывает на закрывающей кавычке.


ШАГ 2. ПАРСЕР

Парсер рекурсивным спуском строит AST. Именно так выглядит вывод --dump-ast:

    FunDecl main(): int32
      Block
        ExprStmt
          Call
            Ident(print)
            StringLit("Hello, World!")
        Return
          IntLit(0)

Дерево пока не знает о типах — это чистая синтаксическая структура.


ШАГ 3. СЕМАНТИЧЕСКИЙ АНАЛИЗ

Первый проход регистрирует main как функцию с нулём параметров и возвратом int32.
Второй проход проверяет тело: print("Hello, World!") — встроенная функция, аргумент string, ок.
return 0 — IntLitExpr без суффикса получает тип int32, совпадает с объявленным возвратом, ок.
Все пути возвращают значение — проверка достижимости пройдена.
После анализа каждый узел выражения помечен своим типом.


ШАГ 4. LOWERING — ПОСТРОЕНИЕ IR

Lowering обходит дерево и порождает трёхадресный код.
Именно это показывает myc examples/hello.bl --dump-ir:

    fun main (0 params, 0 locals):
      print("Hello, World!")
      return 0

Вызов print("Hello, World!") — lowering распознаёт его как встроенный, создаёт IR-инструкцию
Print с операндом ConstString("Hello, World!"). Named_args с end= отсутствуют — обычный Print.
Инструкция return 0 создаёт ReturnVal{ConstInt(0)}.
Временных переменных нет: оба операнда уже константы, вычислять промежуточных результатов не нужно.


ШАГ 5. ОПТИМИЗАТОР

Проходит по IR в два прохода. Первый отслеживает какие временные переменные равны константам.
Второй заменяет операции над двумя константами на Copy с уже вычисленным результатом.
Для hello.bl нечего оптимизировать — нет арифметических выражений с константами.
IR остаётся без изменений.


ШАГ 6. КОДОГЕНЕРАЦИЯ — СБОРКА ФАЙЛА .blc

Кодоген сначала строит индекс функций и добавляет имена в пул, потом генерирует байткод каждой
функции, потом собирает секции в один бинарный файл.

Пул констант после обработки hello.bl содержит три записи:
    pool[0]  тег 0x06 (FNAME)   строка "main"          добавлена при построении индекса функций
    pool[1]  тег 0x05 (STRING)  строка "Hello, World!" добавлена при генерации инструкции Print
    pool[2]  тег 0x01 (INT64)   число 0                добавлена при генерации инструкции RET_VAL

Байткод функции main (8 байт):
    0x01  0x01 0x00    PUSH_CONST 1   положить pool[1] = "Hello, World!" на стек
    0xB0               PRINT          снять со стека, напечатать, добавить \n
    0x01  0x02 0x00    PUSH_CONST 2   положить pool[2] = int64(0) на стек
    0x55               RET_VAL        снять со стека, вернуть как результат функции

Итого: 3+1+3+1 = 8 байт кода.

Заголовок файла (24 байта, все числа little-endian):

    байт  02:     01           версия формата 1
    байт  03:     00           зарезервирован
    байты 04-07:  18 00 00 00  смещение пула констант = 24 (сразу после заголовка)
    байты 08-11:  40 00 00 00  смещение секции функций = 64
    байты 12-15:  5A 00 00 00  смещение отладочных строк = 90
    байты 16-19:  00 00 00 00  индекс функции main = 0
    байты 20-23:  56 00 00 00  смещение глобальных переменных = 86

Пул констант (начиная с байта 24):
    байты 24-27:  03 00 00 00   количество записей = 3
    байт  28:     06            тег FNAME
    байты 29-32:  04 00 00 00   длина строки = 4
    байты 33-36:  6D 61 69 6E  "main"
    байт  37:     05            тег STRING
    байты 38-41:  0D 00 00 00   длина строки = 13
    байты 42-54:  48 65 6C 6C 6F 2C 20 57 6F 72 6C 64 21   "Hello, World!"
    байт  55:     01            тег INT64

Отладочная секция (байт 90):

ШАГ 7. ИСПОЛНЕНИЕ НА ВИРТУАЛЬНОЙ МАШИНЕ

VM загружает файл: читает заголовок, строит пул из трёх записей, строит таблицу из одной функции
с прямым указателем на байты кода, читает ноль глобальных переменных.
Магия "BL" и версия 1 совпадают — загрузка разрешена.

Запуск: вызывается функция с индексом main_idx = 0.
Создаётся первый фрейм: fn = functions[0] (main), pc = 0, slots = [] (0 слотов).

Главный цикл:

    pc=0   читаем байт 0x01 = PUSH_CONST
           читаем 2 байта 01 00 -> индекс = 1
           pool[1] = STRING "Hello, World!" -> Value{Kind::Str, ptr("Hello, World!")}
           кладём на стек;  pc = 3
           Стек: ["Hello, World!"]

    pc=3   читаем байт 0xB0 = PRINT
           снимаем Value{Kind::Str} со стека
           Kind == Str -> cout << *v.str  ->  выводим "Hello, World!"
           затем cout << "\n"             ->  перевод строки
           pc = 4;  Стек: []

    pc=4   читаем байт 0x01 = PUSH_CONST
           читаем 2 байта 02 00 -> индекс = 2
           pool[2] = INT64 0 -> Value{Kind::Int, i=0}
           кладём на стек;  pc = 7
           Стек: [0]

    pc=7   читаем байт 0x55 = RET_VAL
           снимаем Value{Kind::Int, 0} со стека
           frames.pop_back()  -> фреймов не осталось -> выходим из функции
           возвращаем Value{Kind::Int, 0}

Вывод программы: Hello, World!
Код возврата: 0
